# Database migrations

Argus has two ways to get a schema, and exactly one of them should be active per environment.

| Mode | When | How |
|---|---|---|
| `create_all` | development, tests, single-node SQLite pilots | `DB_AUTO_CREATE=true` (default). `init_db()` in `app/core/db.py` calls `Base.metadata.create_all` at startup. Tables are created, never altered. |
| Alembic | staging and production (PostgreSQL) | `DB_AUTO_CREATE=false`. Run `python scripts/migrate.py` before starting the app. The app never touches the schema. |

`assert_safe_config()` already refuses SQLite in production; set `DB_AUTO_CREATE=false` in the
same `.env` so the only schema changes are reviewed migration files.

## Layout

- `alembic.ini` — configuration. The URL is intentionally blank.
- `alembic/env.py` — resolves the URL from `ALEMBIC_DATABASE_URL`, then `DATABASE_URL`, then `.env`
  via `app.core.config.Settings`; imports `app.models` so every package's tables are in
  `Base.metadata`; enables `render_as_batch` for SQLite and `compare_type`.
- `alembic/versions/` — one file per revision. The first one creates every table.
- `scripts/migrate.py` — thin wrapper so operators never need the `alembic` CLI on the PATH.

## Everyday commands

```bash
# upgrade to the newest revision (what deploy pipelines run)
python scripts/migrate.py

# show where the database is
python scripts/migrate.py --current

# fail CI when a model changed without a migration
python scripts/migrate.py --check

# generate a migration after changing models (review the file before committing it)
alembic revision --autogenerate -m "add foo column"

# print SQL for a DBA instead of executing
python scripts/migrate.py --sql
```

Set `ALEMBIC_DATABASE_URL` to point autogenerate at a scratch database so it diffs against an
empty or known schema rather than your working database.

## Adopting Alembic on an existing `create_all` database

The initial revision creates every table, so running it against a database that already has
them fails. Stamp instead:

```bash
python scripts/migrate.py --stamp head
```

From then on only `scripts/migrate.py` (upgrade) changes the schema.

## Rules for migration authors

- Every table carries `tenant_id` (`TenantMixin`); indexes on `(tenant_id, …)` are part of the
  model and therefore of the autogenerated diff.
- Never put data backfills that read secrets or PII into a migration; use a one-off script that
  goes through the application's redaction helpers.
- SQLite cannot `ALTER COLUMN`; `render_as_batch` rewrites tables for you, but test the file
  against both SQLite and PostgreSQL before merging.
- Downgrades must be real. If a step is irreversible (dropping a column with data), say so in the
  docstring and make `downgrade()` raise instead of silently passing.
- The audit table is append-only by contract: no migration may rewrite `audit.entry_hash`,
  `previous_hash` or `signature`. A migration that reorders or deletes audit rows breaks
  `verify_chain()` and must not be written.
